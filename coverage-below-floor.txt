# coverage-below-floor.txt — the shipping projects under the coverage floor, the rate each is held
# to, and why.
#
# docs/plan/23 § Test layers, row Unit: "Coverage ≥ 70 % per project". A project listed here is
# below it and is known to be, and the number beside it is the rate measured the day the row was
# written. The row buys exemption from the floor and from nothing else.
#
# Enforced in FOUR directions by Build.Test.cs § EnforceCoverageFloor, through
# CoverageReport.cs § Violations:
#
#   * a project below 70 % that is NOT listed here fails the build. That is the floor, unchanged,
#     and it is the durable half — the next project to slide cannot do it quietly;
#   * a listed project measured more than half a point BELOW its pinned rate fails. The pin only
#     moves one way, so debt already written down cannot grow behind the row that records it;
#   * a listed project measured more than half a point ABOVE its pin fails, asking for the pin to be
#     raised. Without this the tolerance would be a budget: a project could sit fractionally under
#     its pin forever and walk ten points down a tenth at a time inside the rules. The pin is the
#     measurement of record, and a stale one gives back ground somebody won;
#   * a listed project that now MEETS 70 % fails, demanding its row be deleted. A debt list that
#     outlives its debt is one nobody can tell the live rows in, and at that point it stops being
#     evidence and becomes an exemption list — which is the thing the floor's own failure message
#     says never to build.
#
# ⚠ ADDING A ROW IS A REVIEW REQUEST, NOT A BUILD FIX. The question a reviewer is being asked is
# "should this project ship under-tested, and is this number the honest measure of how far?". The
# answer is almost always no, and the fix is a test. It is yes only when what is uncovered cannot be
# covered by a unit test for a reason that is written down — a composition root, a path that needs a
# real cluster — AND the test that would cover it is named somewhere as owed. Both halves. "No time
# this sprint" is not a reason; it is a reason to write the test.
#
# ⚠ EVERY ROW NEEDS A SENTENCE DIRECTLY ABOVE IT, with no blank line between, saying what is
# uncovered and what closing it would take. The parser refuses a row without one. A reviewer cannot
# answer a review request that is a name and a number, and a list that costs a sentence to extend is
# a list that stays short.
#
# One project per line: the project name, whitespace, the measured rate as a percentage with one
# decimal. Blank lines and lines starting with `#` are ignored. The rate is compared with a
# tolerance of half a percentage point in both directions — CoverageReport.cs § PinTolerance says
# why that number and why it cannot be spent.
#
# ⚠ ALL SIX RULES WERE SABOTAGE-TESTED ON 2026-08-20, not merely observed passing. Each was made to
# fail on purpose and the failure was read:
#
#   blank line between a reason and its row   → refused in under a second, naming the line
#   a rate of 72.0                            → refused: "a pin at or above the floor is not debt"
#   the same project listed twice             → refused, naming both lines
#   CyberCloud.Silo.Host pinned at 40.0       → "DROPPED by 7.5 point(s)"
#   CyberCloud.Vault (81.3 %) added as a row  → "meets the 70 % floor … delete that row"
#   CyberCloud.Silo.Host pinned at 20.0       → "IMPROVED by 12.5 point(s). Raise the pin to 32.5"
#   the CyberCloud.Silo.Host row deleted      → "below the 70 % floor … the fix is a test"
#
# The first three fail before a single suite starts, which is deliberate: a typo in this file is a
# typo, and finding one at the end of a ten-minute test run is how a file becomes something people
# edit by copying a line and hoping.

# ── 2026-08-20: the first honest local measurement this repository has ever had ─────────────────
#
# ⚠ Read this before adding anything, because the numbers this file replaced were wrong and the way
# they were wrong is instructive.
#
# Until this date the floor had never run anywhere a developer could see it. `dotnet-coverage`
# 18.9.0 ships no arm64 profiler, so on every Apple Silicon machine `./build.sh Test` printed ○ —
# "the coverage floor was NOT ENFORCED" — and an x64 CI runner was the only place a number was ever
# produced. Switching the collector to coverlet, which rewrites IL and needs no profiler, made the
# gate visible here for the first time. Two bugs in the reading of the report came out with it:
#
#   * `CoverageReport.Read` took a line's filename from its GRANDPARENT, which is the <method> for
#     the copy Cobertura writes under <method><lines>, and <method> carries no filename. Every
#     method-level line therefore keyed as (assembly, "", number): counted twice, and line 17 of one
#     file collapsed into line 17 of every other. That inflated CyberCloud.Identity to 66.2 % from a
#     true 64.4 %. The previously-circulated figures of Identity 66.8 % and Identity.Host 39.6 %
#     came from this reading and were both high.
#
#   * A `filename` is relative to its own report's <sources> root, and coverlet writes the deepest
#     directory common to what it instrumented — so 56 of one run's 71 reports said the repository
#     root and 15 said `src/`. Keying on the raw string split one file into two, counted its lines
#     twice, and never unioned the two hit sets, so a line covered by one suite read as uncovered
#     because another suite spelled the path differently. This one DEFLATED, badly.
#
# The second bug is why this file has one row rather than six. Measured before it was fixed, six
# projects looked as though they breached the floor; measured after, five of them never did:
#
#   CyberCloud.Communication            49.6 % → 70.8 %
#   CyberCloud.Communication.Contracts  64.0 % → 92.1 %
#   CyberCloud.Kubernetes               54.6 % → 77.3 %
#   CyberCloud.ServiceDefaults          59.6 % → 88.4 %
#   CyberCloud.Tenancy                  60.6 % → 86.8 %
#   CyberCloud.Silo.Host                32.5 % → 32.5 %   ← the only real one
#
# They are written down because a list of five projects that "used to be in the baseline" is exactly
# what somebody re-adds from memory. None of them belongs here. ⚠ CyberCloud.Communication is at
# 70.8 %, which clears the floor by eight tenths of a point — it is the row this file is most likely
# to gain next, and the answer when that happens is a test.

# ── 2026-09-03: this row measures WHERE THE CODE RUNS, not how well it is tested ────────────────
#
# ⚠ THE ONE SENTENCE, BECAUSE IT EXPLAINS EVERYTHING BELOW IT: coverlet instruments
# `artifacts/bin/<suite>/`, and Aspire launches the silo from `artifacts/bin/CyberCloud.Silo.Host/`.
# So the code this host exists to run is exercised — hard, by CyberCloud.AppHost.Tests, against two
# real silo processes, a real Redis and a real PostgreSQL — in processes the collector never
# instrumented. What this row records is a MEASUREMENT BOUNDARY, not a testing gap.
#
# The paragraph this replaced said three things, and the sentence above is why none of them was true:
#
#   * "Covering LocalKubeconfigFiles.cs alone would take this project past the floor and this row
#     out of the file." ⚠ IT CANNOT, AND COULD NOT ON THE DAY IT WAS WRITTEN. The assembly has 256
#     coverable lines. `HelloGrain.cs` (46) and `Program.cs` (32) are 78 of them that no in-process
#     unit test reaches, so the ceiling is 178/256 = 69.5 % — under the floor before one other line
#     is counted. The file IS covered now, by CyberCloud.Silo.Host.Tests, and the first test that
#     ran against it found a real defect (a bare path parsed as a `file:` URI on Linux and not on
#     Windows). That work moved the rate 32.5 % → 58.6 %, which is all it could ever have bought.
#
#   * "HelloGrain.cs — nothing calls it but a human." Eight call sites call it, across
#     Phase0ExitCriterionTests and TwoSiloClusterTests, through a real Orleans client: it is
#     docs/plan/24 § Phase 0's exit-criterion subject and the only thing in the tree that proves both
#     storage tiers are wired at once. ⚠ DELETING IT TO MOVE THIS NUMBER WOULD DELETE THE CRITERION.
#     It reads as 0 % because of the sentence at the top, and for no other reason.
#
#   * "Program.cs is the composition root — it builds a host and runs it." It also holds the
#     `--apply-durable-schema` job mode, a second entry point with real branching that is the thing
#     making a fresh PostgreSQL shard usable at all, and the AppHost runs it as a WaitForCompletion
#     resource. Also exercised, also out of process.
#
# THE THREE WAYS OUT, and why this change took the first:
#
#   raise the pin and rewrite this reason — done here. Truthful, and it buys nothing: the row stays,
#     and a row that can never be deleted is the permanent exemption this file's own rules refuse to
#     build. It is the right holding position and the wrong destination.
#   [ExcludeFromCodeCoverage] on the two out-of-process entry points — CoverageReport.cs § CoverableLines
#     already subtracts it and coverlet already honours it, so it needs no build change; it would put
#     this project near 83 % and delete this row. ⚠ IT IS A REVIEW REQUEST AND NOT A REPAIR, and it
#     was deliberately not applied by the change that would have benefited from it: nothing in src/
#     uses that attribute today, so it is a new policy, and the same attribute that honestly excludes
#     a process the collector cannot reach is the fastest way for the next project under the floor to
#     stop being under it. Adopt it only with the written reason this file already demands of a row.
#   instrument the silo processes — ⚠ THE ONLY ONE THAT MAKES THE NUMBER MEAN WHAT THE FLOOR THINKS
#     IT MEANS, rather than making it smaller. coverlet would have to instrument
#     artifacts/bin/CyberCloud.Silo.Host/ and merge reports written by processes Aspire launches and
#     kills. Owed, and named here so the other two are read as what they are.
#
# ⚠ ASKED AND ANSWERED FOR THE NEXT ROW, because a boundary nobody has scoped is a boundary that
# turns up again: CyberCloud.Silo.Host is the ONLY project this affects. CyberCloud.AppHost's
# Program.cs is the only thing that launches a project as a process, and the only project it launches
# is this one — three times, as the durable-schema job and the two silos. Everything else measured by
# this floor runs inside the suite that tests it.
#
# In particular CyberCloud.Communication, which clears the floor by eight tenths of a point and is the
# row this file is most likely to gain next, is NOT affected: its grains activate in an in-process
# TestCluster (CommunicationCluster.cs), inside the instrumented process, so its 70.8 % is honestly
# earned and the answer when it slips is still a test. ⚠ Note the direction — this boundary can only
# DEFLATE a rate, never inflate one. A line covered in the instrumented process is really covered;
# out-of-process execution simply adds nothing. So no row here is flattered by it, and no green
# project is secretly red.
CyberCloud.Silo.Host                              58.6
