# durable-grains.txt — the grain types whose state is durable.
#
# docs/plan/05 § Choosing a tier: "every grain type in durable-grains.txt must bind its primary
# state to Durable, and any grain type not on the list that binds to Durable must carry
# [DurableStateRationale("…")]. The list is reviewed like a schema migration, because that is what
# it is."
#
# Enforced in both directions by the Storage tier gate in build/Build.Architecture.cs. Both
# directions catch a different mistake:
#
#   * a line here whose grain no longer binds Durable is state that silently became rebuildable,
#     and the loss is discovered by a customer;
#   * a grain binding Durable that is not here is a schema change nobody reviewed.
#
# ⚠ ADDING A LINE IS A REVIEW REQUEST, NOT A BUILD FIX. docs/plan/02 § ADR-003 puts the loss
# tolerance of this tier at zero: every entry below is PostgreSQL, sharded by tenant, on a
# synchronous replica, in every backup. If the honest answer is "this can be rebuilt", the tier is
# Hot and the line does not belong here.
#
# One fully-qualified grain type per line, as the CLR names it — namespace, type, and `+` before a
# nested type. Blank lines and lines starting with `#` are ignored. Test fixtures are out of scope;
# the gate reads shipping assemblies only.

# ── Tenancy — docs/plan/06 ─────────────────────────────────────────────────────────────────────
# The tenant, what it has bought, and how its resources are grouped. The directory and the shard
# map are the two null-tenant platform grains of docs/plan/05 § The shard map: losing either one
# means no tenant can be located, so "rebuildable" is not a property they have.
CyberCloud.Tenancy.TenantGrain
CyberCloud.Tenancy.TenantDirectoryGrain
CyberCloud.Tenancy.ShardMapGrain
CyberCloud.Tenancy.SubscriptionGrain
CyberCloud.Tenancy.ResourceGroupGrain
# The scope above the subscription (issue #39). Role assignments are scoped to it, so losing the
# record would detach every grant made at it while the tuples still named it.
CyberCloud.Tenancy.ManagementGroupGrain
CyberCloud.Tenancy.QuotaGrain

# The indexes. Rebuildable in principle by scanning every tenant, which is exactly the operation
# that is impossible during the incident where you need them. The client index maps an OAuth
# client_id to its application — docs/plan/11 § Protocol — and losing it would let a second
# application claim a client_id a token was already issued to.
CyberCloud.Tenancy.ResourceIndexGrain
CyberCloud.Tenancy.EmailIndexGrain
CyberCloud.Tenancy.ClientIndexGrain

# ── Authorization — docs/plan/07 ───────────────────────────────────────────────────────────────
# The ReBAC tuples and both of their indexes. These are the answer to "who may do what": losing a
# tuple does not degrade a permission check, it silently reverses it.
CyberCloud.Authorization.Grains.TupleStoreGrain
CyberCloud.Authorization.Grains.ObjectRelationsGrain
CyberCloud.Authorization.Grains.SubjectRelationsGrain
#
# ⚠ CyberCloud.Authorization.Grains.MembershipIndexGrain — the Leopard index of
# docs/plan/07 § The Leopard index — binds Durable and is deliberately NOT a line here. It is a
# closure derived from the two indexes above and recomputed from them by RebuildAsync, so its loss
# tolerance is not zero. It carries [DurableStateRationale] saying why it is Durable rather than Hot
# regardless: the store writes it under its journal, before the relation version moves, and a Redis
# flush would leave it behind every outstanding token with nothing to replay.

# ── Kubernetes — docs/plan/09 ──────────────────────────────────────────────────────────────────
# How to reach a tenant's cluster. The informer cursors on this grain are the cheap thing kept so
# the expensive thing — the informer cache — can be rebuilt; see ClusterConnectionState.
CyberCloud.Kubernetes.Connections.ClusterConnectionGrain
#
# AgentTunnelGrain is the connected cluster's other half (docs/plan/09 § Cluster connections, the
# AgentInitiated row, #36): who owns the cluster, the hash of the enrollment token that admits its
# agent, the hash of the credential that agent was handed in exchange, and when it last heartbeated.
# docs/plan/05 § Choosing a tier's test — "can this be rebuilt" — answers no in the direction that
# matters: the credential's plaintext exists in exactly one place, a Secret in the TENANT's cluster,
# and losing its hash means every connected cluster's agent presents a credential the platform no
# longer recognises. The "rebuild" is the tenant re-running listInstallCommand and re-installing the
# agent, on every cluster, after a platform incident — a customer-visible outage rather than a cache
# miss. The session — the socket, the requests in flight — is in memory and is NOT durable; a lost
# session is one reconnect, which the agent does on its own.
CyberCloud.Kubernetes.Tunnel.AgentTunnelGrain

# ── Resource manager — docs/plan/08 ────────────────────────────────────────────────────────────
# The tenant's declared intent, and the record of what is being done about it.
#
# ResourceGrain holds desired state. docs/plan/02 § ADR-001 makes this the system of record — "the
# cluster can be wiped and rebuilt from grain state; grain state cannot be rebuilt from the
# cluster" — so losing it loses what the tenant asked for, with running pods and no owner.
# Observed state is separately bound to Hot, which is the split docs/plan/05 § Choosing a tier
# describes and is why only one of the two bindings is on this list.
CyberCloud.ResourceManager.Grains.ResourceGrain
#
# OperationGrain is durable because docs/plan/00 § Non-negotiables makes every long-running
# operation resumable, and docs/plan/08 § Long-running operations spells out what that costs: the
# state "includes everything needed to re-drive — the resource id, the desired body, the quota
# lease, the index claim, the step cursor". Losing it strands a resource mid-provision in exactly
# the Creating-forever state the chaos suite exists to forbid.
CyberCloud.ResourceManager.Grains.OperationGrain
#
# ParkedResourceRegistryGrain is the per-resource-group list of what is inside its soft-delete
# recovery window — docs/plan/08 § Soft delete, issue #71. Every other fact about a parked resource
# has a second home: the name is held by ResourceIndexGrain, the body by ResourceGrain, the
# committed quota by QuotaGrain, and all three are already on this list. The ENUMERATION has none,
# and that is the whole reason this grain exists. The index is one grain per path and one-way, so
# ResolveSoftDeletedAsync answers only a question you can already ask; the group's membership
# deliberately no longer holds the resource, because a member left behind would put a name into a
# listing whose every read is the canonical 404; and nothing scans, because there is nothing to scan.
#
# So docs/plan/05 § Choosing a tier's test — "if the honest answer is 'this can be rebuilt', the tier
# is Hot" — answers no, and it answers no in the sharper direction: losing this does not degrade a
# listing, it silently empties it. A resource whose entry is gone is still parked, still holding its
# name and its committed quota for the rest of its window, and reachable only by somebody who
# remembers the exact path — which is the state issue #71 was filed about, restored one flush at a
# time and visible to nobody.
CyberCloud.ResourceManager.Grains.ParkedResourceRegistryGrain
#
# ResourceWatchGrain is the per-(subscription, type) list of resources that asked to hear when
# resources of that type change — docs/plan/08 § What the resource manager deliberately does not
# do, the cross-resource seam of issue #90. The test above answers no for the reason it does for the
# parked registry: the enumeration has no second home. A watch is registered by a reconciler, and a
# reconciler holds nothing between passes (docs/plan/08 § The reconcile loop, clause 2) — its next
# pass will re-register, but the passes in between are the ones the fan-out has to find it on, and a
# fan-out reading an empty set after a silo restart delivers nothing and reports nothing wrong. A
# vault that missed the change to a share it protects is a backup that silently stopped covering it.
CyberCloud.ResourceManager.Grains.ResourceWatchGrain

# ── Metering — docs/plan/22 ────────────────────────────────────────────────────────────────────
# The two halves of "a usage record, once emitted, is never lost and never double-counted"
# (docs/plan/22, opening). Both are on this list because neither is rebuildable, and the reason is
# the same sentence in docs/plan/22 § Effort that puts metering in M1 and invoicing in M2: "usage
# that was never recorded cannot be recovered".
#
# UsageRollupGrain holds two things. The first is raw usage for hours that have not closed — the
# sample window has passed, the resource may since have been deleted, and there is nowhere to read
# it from again. The second is the set of idempotency keys already seen, and losing THAT is worse
# than losing the records: a lost record is a figure that is too low and shows up as a dip in a
# graph, while a forgotten key turns every redelivery inside the seven-day horizon into a double
# charge that looks like growth. Delivery is at-least-once (docs/plan/04 § Streams), so redelivery
# is the expected path after a silo restart and not an edge case.
CyberCloud.Metering.Grains.UsageRollupGrain
#
# UsageLedgerGrain is the append-only record of account — docs/plan/22 § The pipeline: "The ledger
# is durable-tier and append-only. Corrections are new entries with a reason and a link to the
# original, never edits. An adjustable ledger cannot be audited and cannot be defended in a
# dispute." Durable is the tier that sentence names. ⚠ It is also the one grain here whose loss
# tolerance is legal rather than operational: this is what an invoice is derived from and what a
# customer's dispute is argued against, and ADR-003's zero is the only defensible figure.
#
# ⚠ Read this entry as the M1 half of docs/plan/22 § Effort's "ledger grain" row, which that table
# puts in M2. The M2 row is a ledger of CHARGES and needs prices, which M1 does not have. This is
# the ledger of USAGE — quantities, not money — and it is M1 because the meters must be correct
# from the first resource. When rating lands, charges are a second ledger derived from this one and
# this one does not change.
CyberCloud.Metering.Grains.UsageLedgerGrain
#
# ⚠ NOT UsageSamplerGrain, and the absence is reviewed rather than forgotten. Its state is a cursor
# saying which window it last sampled. Losing it makes the sampler re-sample the current window,
# which produces records carrying the SAME idempotency keys, which UsageRollupGrain collapses — so
# the loss costs one redundant pass and nothing else. docs/plan/05 § Choosing a tier's test ("if the
# honest answer is 'this can be rebuilt', the tier is Hot") answers cleanly, and it answers that way
# only because the dedup above is durable.

# ── Billing — docs/plan/22, issue #38 ──────────────────────────────────────────────────────────
# ⚠ WHAT THE ENTRY ABOVE CALLED "A SECOND LEDGER DERIVED FROM THIS ONE" DID NOT SHIP AS A LEDGER.
# Charges are not stored: a draft invoice, a cost row and a budget's figure are all the usage ledger
# rated on the day they are asked for (CyberCloud.Billing.Pricing.UsagePricing), so there is nothing
# about money that could disagree with the usage it was derived from. What IS stored is what cannot
# be derived again, and that is three grains:
#
# BillingAccountGrain holds the finalized invoices and the credit notes — documents a customer has
# been sent, whose integrity must be kept for the whole storage period (Council Directive
# 2006/112/EC, Articles 233 and 247) and which no re-rating reproduces once the price sheet or the ledger has
# moved on. Loss tolerance is legal, not operational, as the usage ledger's is.
CyberCloud.Billing.Grains.BillingAccountGrain
#
# InvoiceNumberingGrain holds the gap-free sequences. Losing it restarts numbering at 1: every new
# invoice then carries a number an existing one already has, which is the defect a sequential
# invoice number exists to make impossible.
CyberCloud.Billing.Grains.InvoiceNumberingGrain
#
# BudgetGrain holds which thresholds have fired this period. A forgotten one fires again on the
# next tick, and the sending module's idempotency key is the only thing between that and a second
# page to finance — a second defence is not a reason to lose the first.
CyberCloud.Billing.Grains.BudgetGrain
#
# ⚠ NOT CostQueryGrain, which holds nothing: it is a stateless worker over the ledger and the check
# grains, and has no [PersistentState] to bind. Nor InvoiceQueryGrain (#41), a stateless worker over
# the billing account and one check grain, for the same reason.

# ── Providers — docs/plan/03 § Providers ───────────────────────────────────────────────────────
# THREE, since #32, #29 and the key vault — and for fifteen families before them NOTHING, an absence that was the
# reviewed decision rather than an omission.
#
# CyberCloud.Providers.Sample is the first provider (docs/plan/24 § Phase 1, exit criterion 1) and
# it declares no grain of its own. A widget's desired state is held by ResourceGrain above, which is
# already on this list; its observed state is a ConfigMap in a cluster, which ADR-001 makes
# rebuildable from that desired state by construction — "the cluster can be wiped and rebuilt from
# grain state; grain state cannot be rebuilt from the cluster". Every family up to the fifteenth
# had the same shape, and the paragraph that stood here said: the day a provider does need a line
# here, the first question is what the manager is missing.
#
# ⚠ Read this as a measurement, not as a note. docs/plan/25 § R1's leading indicator is how much a
# provider has to add to the platform, and a provider that needed durable state of its own would be
# holding something the resource manager should have been holding for it. The day a provider does
# need a line here, the first question is what the manager is missing.
#
# ⚠ THE DAY CAME WITH CyberCloud.Monitor/workspaces/alertRules, AND THE QUESTION HAS AN ANSWER THAT
# IS NOT "THE MANAGER". The manager holds one desired body and one observed state per resource. An
# alert rule's memory is neither: it is a SEQUENCE — when the condition started holding, when it
# fired, whether each recipient was told and what the sending module said if not, when it resolved —
# and a manager that held a history per resource would be holding it for every type that has none.
# docs/plan/05 § Choosing a tier's test ("if the honest answer is 'this can be rebuilt', the tier is
# Hot") answers no in the sharp direction: the samples that fired an alert age out of the store in
# days, and whether a page was SENT was never in any store but this one. A tenant reading the history
# at 03:00 to learn whether they were told is docs/plan/16 § Cost and retention honesty's closing
# sentence applied to a page rather than a log line — a monitoring product that quietly loses one is
# trusted. The open instance is also what a re-drive after a silo move reads to NOT page twice: its
# id is half of every idempotency key sent about it, and losing it would mint a second.
#
# ⚠ AND IT IS PER WORKSPACE, NOT PER RULE, so the row count is the workspace count and the reminder
# count is too — docs/plan/04 § Reminders' scaling arithmetic, answered by the key rather than by a
# cap. IAlertEvaluatorGrain carries the argument; the action group's recipients are the one thing in
# the state a person might mistake for sensitive, and they are what a notification is addressed to.
CyberCloud.Providers.Monitor.Alerting.AlertEvaluatorGrain
#
# ⚠ THE QUESTION WAS ASKED, AND THE ANSWER IS THAT THE MANAGER IS MISSING NOTHING. FeedGrain is the
# catalogue of CyberCloud.ContainerRegistry/feeds (docs/plan/13 § Artifact feeds): which versions of
# which packages tenants have PUSHED INTO the feed, which are listed, what each hashes to, where its
# bytes are, and where each npm dist-tag points. ResourceGrain holds the tenant's declared intent —
# a feed's kind and description — and that is the whole of what the write path ever sees. The
# catalogue is data-plane content that arrives through `dotnet nuget push` on a host the manager
# never routes, the way rows arrive in a managed database through a connection string; the manager
# holds no database's rows either, and holding a feed's would make it the second copy docs/plan/25
# § R1 warns about, one layer up. So this is the first provider grain, and it is not a manager gap.
#
# ⚠ DURABLE AND NOT HOT, BY docs/plan/05 § Choosing a tier's test, and the test answers sharply.
# The bytes are in the object store, so "can this be rebuilt" sounds like yes — list the prefix,
# open every nupkg for its nuspec, every tarball for its package.json. It is no, three times: an
# unlisting, an npm dist-tag and a NuGet publish timestamp exist nowhere but here, and a rebuild
# would re-list every unlisted version, point every `latest` at whatever sorted last, and reset every
# `published` to the day of the incident. The reverse-index paragraph above applies too: a scan of
# every feed of every tenant is exactly the operation that is impossible during the incident where
# you need it.
CyberCloud.Providers.ContainerRegistry.FeedGrain
#
# ⚠ THE THIRD PROVIDER GRAIN, AND THE MANAGER IS MISSING NOTHING HERE EITHER. KeyVaultGrain holds what
# a tenant put INTO a CyberCloud.KeyVault/vaults through its data plane (docs/plan/18 § The resource
# model): every version of every secret and key, their enabled/expiry attributes, and which are
# soft-deleted until when. ResourceGrain holds the vault's declared intent — its purge protection and
# its description — and nothing else; a secret's value in a desired body would be a secret handed to
# every `read` holder and written into every backup of ResourceGrain.
#
# ⚠ DURABLE, AND THE TEST ANSWERS IN THE SHARPEST DIRECTION OF ANY LINE IN THIS FILE. "Can this be
# rebuilt" — no, from anywhere: a generated key's private half exists nowhere else by design, so losing
# this state is losing the key, and every ciphertext and signature made with it becomes unopenable and
# unverifiable. docs/plan/18 § The resource model calls a deleted signing key "a business-ending
# event"; a flushed one is the same event without the seven days. And the soft-deleted half is a
# promise with a date on it: an item inside its recovery window must still be recoverable after an
# incident.
#
# ⚠ AND NOTHING IN IT IS A SECRET IN CC1005'S SENSE, WHICH IS WHY IT MAY BE HERE AT ALL. Every value and
# every private key is AES-256-GCM ciphertext under a per-vault root that lives in OpenBao, minted by the
# reconciler through ISecretWriter and never written to any grain; a backup of this tier opens nothing
# without the platform vault. KeyVaultGrainTests.TheDurableStateHoldsNoValueAndNoKeyMaterial reads the
# stored state back and searches it for the plaintext.
CyberCloud.Providers.KeyVault.KeyVaultGrain
#
# ⚠ The measurement docs/plan/25 § R1 asks for is still being taken, and this line is part of it:
# what the feeds provider added to the platform was not a grain the manager should have held but a
# SEAM — IObjectStore on ReconcileContext, beside ISecretResolver — which is the manager growing a
# capability rather than a provider working round its absence.

# ── Communication — docs/plan/17 ───────────────────────────────────────────────────────────────
# The sending product's four pieces of state that a person, a carrier or a regulator would notice
# the loss of. docs/plan/17 § The parts that are actually the work puts MESSAGE grains in the hot
# tier and is right to; everything below is the other kind of state, and each entry says why.
#
# SuppressionListGrain is the one entry here that is not arguable. It holds bounces, complaints and
# opt-outs, "per tenant, honoured before dispatch" — docs/plan/17 § The parts that are actually the
# work, which adds "ignoring a complaint is how a sending domain gets blocked". docs/plan/05
# § Choosing a tier asks whether the state can be rebuilt, and here the upstream is a person who
# already told us to stop: losing the list does not degrade sending, it silently REVERSES a consent
# decision, and the platform then messages everyone who opted out. That is a regulatory finding in
# most jurisdictions and, in the US, a statutory penalty per message. ⚠ Rebuilding it would mean
# asking every recipient again, which is itself the thing they asked us not to do.
CyberCloud.Communication.Grains.SuppressionListGrain
#
# CommunicationServiceGrain holds a paying customer's carrier wiring: which provider each channel
# uses, whose account pays, the vault HANDLES for their own credentials (never the values — CC1005),
# and the per-window spend caps. Nothing upstream holds any of it; the tenant does, in their head,
# and asking them to re-enter it is asking them to redo the onboarding they paid for. The caps are
# the sharper half — ChannelLimits.None is the default, so a lost configuration does not overspend,
# it stops sending entirely and every OTP in the platform fails at once.
CyberCloud.Communication.Grains.CommunicationServiceGrain
#
# MessageTemplateGrain holds template versions and, for WhatsApp, the carrier's approval of each
# BODY. docs/plan/17 § The parts that are actually the work: "WhatsApp requires pre-approved
# templates." An approval is attached to that exact text, so losing our copy is not losing a cache —
# it is resubmitting and waiting days with business-initiated WhatsApp sending down. "Can this be
# rebuilt" answers no, and the recovery is a queue at Meta rather than a warm-up.
CyberCloud.Communication.Grains.MessageTemplateGrain
#
# SenderIdentityGrain is a compliance record: what the tenant submitted for sender-id registration
# or a 10DLC campaign, what the carrier answered, and which countries were cleared. docs/plan/17
# § The channel abstraction makes those the tenant's obligations with our tooling, which means our
# copy is the evidence — and the question it answers ("what were you approved for, and by whom")
# arrives months later from somebody with the authority to ask.
CyberCloud.Communication.Grains.SenderIdentityGrain
#
# ⚠ NOT MessageGrain, NOT SendLimitGrain and NOT ProviderMessageIndexGrain, and all three absences
# are reviewed rather than forgotten.
#
# MessageGrain is Hot because docs/plan/17 § The parts that are actually the work says so directly —
# "message grains (hot tier, TTL'd)" — and the argument survives docs/plan/05 § Choosing a tier's
# test. What a flush loses is the ability to answer "did it arrive" for messages inside the
# retention window, and the ability to collapse a retry that arrives after it. Neither is a record
# of account: the money is metering's durable ledger and the trail is the audit log. ⚠ The cost is
# real and is stated rather than hidden — a hot-tier loss inside the window turns a retry into a
# second send, which is the exact harm idempotency exists to prevent. It is bounded: a FLUSHALL is a
# declared incident (docs/plan/05 § Hot), and the alternative is a synchronously-replicated write on
# the path an OTP travels, with a user waiting at a login form, forever.
#
# SendLimitGrain holds counters and never the caps — the caps live on CommunicationServiceGrain
# above, which is durable. That split is what bounds a hot-tier loss to one window's counters
# instead of resetting every tenant's cap, and docs/plan/05 § Hot already lists "rate-limit
# counters" among what the hot tier holds. The backstop if a window is ever in doubt is metering's
# ledger, which is the durable record of what was actually sent.
#
# ProviderMessageIndexGrain maps a carrier's message id back to ours and must expire with the
# message it points at. An index entry that outlived its message would resurrect an empty activation
# on every late webhook, so it is Hot for the same reason and to the same horizon.

# ── Identity — docs/plan/11 ────────────────────────────────────────────────────────────────────
# Who may sign in, and with what. docs/plan/02 § ADR-003 puts the loss tolerance of this tier at
# zero, and for these four the honest answer to "can this be rebuilt" is no, in a way that is worse
# than for most durable state: there is no upstream to re-read from, because the identity system IS
# the upstream. Losing a user's credentials locks a person out of an account they still own, with no
# recovery that does not go through a support process and an out-of-band identity proof.
#
# UserGrain holds the password hash, the enrolled passkeys, the recovery-code hashes, the vault
# handle for the TOTP secret, and the spent-TOTP-counter set. The last one is the least obvious and
# is the reason this cannot be Hot even in part: losing the spent counters would let a code observed
# over somebody's shoulder be replayed inside its 90-second window, which docs/plan/11 § Credentials
# specifically requires be blocked per (user, counter).
CyberCloud.Identity.Grains.UserGrain
#
# GroupGrain holds the group's IDENTITY only — name, description, created-at. Its membership is
# deliberately NOT here: docs/plan/11 § The object model puts that in ReBAC tuples, which are
# already on this list under CyberCloud.Authorization. The group object is still durable because the
# GUID in its key is the ReBAC object id, so losing the object orphans every tuple naming it and
# every role assignment made to its `member` userset — a silent, total revocation.
CyberCloud.Identity.Grains.GroupGrain
#
# ApplicationGrain is the OAuth client registration: redirect URIs, grant types, scopes. Losing one
# breaks every sign-in through that client, and the redirect URIs in particular are a security
# control — a registration rebuilt from memory by an operator under pressure is how a wrong URI gets
# allowed.
CyberCloud.Identity.Grains.ApplicationGrain
#
# ServicePrincipalGrain is a machine identity and its vault handle. Losing it breaks every CI job
# and integration authenticating as it, and there is no user to notice and re-enrol.
CyberCloud.Identity.Grains.ServicePrincipalGrain
#
# ManagedIdentityGrain holds a workload's (cluster, namespace, serviceAccount) binding and the
# cluster's OIDC issuer and public key set — docs/plan/11 § Managed identity, steps 2 and 3.
#
# ⚠ Read this line carefully, because the obvious argument goes the other way. Nothing on this grain
# is secret: the key set is the public half of a signing pair, served unauthenticated by the
# tenant's own API server, and the binding names a namespace rather than holding a credential. So
# "is it sensitive" answers no — and that is not the question docs/plan/05 § Choosing a tier asks.
# The question is "can this be rebuilt", and it cannot: the binding is a decision a tenant
# administrator made, recorded nowhere else. There is no cluster to re-read it from, because the
# cluster does not know which platform identity its service account was mapped to. Losing it does
# not degrade authentication, it REVERSES it — every workload in the tenant stops being able to
# exchange, and the only recovery is a human re-entering bindings they may not have written down.
#
# The issuer record beside it is genuinely rebuildable — RefreshIssuerAsync re-reads it — but it is
# rebuildable only FROM the binding, so splitting the two across tiers would buy nothing and add a
# state machine where a crash between two writes leaves an identity trusting a cluster it is no
# longer bound to.
CyberCloud.Identity.Grains.ManagedIdentityGrain
#
# ConsentGrain is a person's standing consent to one tenant-registered OAuth client, and the scopes
# it covers — docs/plan/11 § Protocol, the consent page (#94). Losing one is SAFE in the direction
# that matters (the person is asked again rather than a client being trusted it should not be), so
# the tier question is not loss tolerance but shape: docs/plan/05 § Hot holds "session-shaped state,
# which is bounded by concurrent activity, not by tenant size", and consent grants are bounded by
# users × clients, which is tenant size. A hot-tier FLUSHALL would also re-prompt every third-party
# integration in every tenant at once, which is a loss a person notices even though it is not one
# that reverses a permission. Revocation empties the record rather than deleting it, so a revoked
# client is asked from scratch.
CyberCloud.Identity.Grains.ConsentGrain
#
# ⚠ SessionGrain is deliberately ABSENT. docs/plan/05 § Hot lists sessions among what the hot tier
# holds: losing one costs a sign-in, which is a warm-up rather than a loss. It is also the
# highest-write-rate object in the identity module — every refresh rotation is a write — so putting
# it on a synchronously-replicated shard would make the refresh endpoint the slowest thing in the
# platform, for state whose loss tolerance is a re-authentication.
#
# ⚠ AuthorizationCodeGrain is ABSENT for the same reason, and more so. It records that one
# authorization code has been exchanged, and by which token session, so a second exchange is refused
# and the first one's session revoked (RFC 6749 § 4.1.2, #94). The record protects nothing once the
# code it names has expired — five minutes — and the grain clears itself then; losing the tier early
# costs one replay window on the codes in flight at that moment, each still bound to its verifier by
# PKCE. Session-shaped, bounded by concurrent sign-ins, and written once per sign-in on the path a
# person is waiting on.
#
# ⚠ DeviceAuthorizationGrain is ABSENT for AuthorizationCodeGrain's reason (#43). It is one RFC 8628
# device authorization — the codes `cyc login` on a headless box prints, and the person's answer —
# and it is worth ten minutes: past them the codes are refused whatever the tier holds, and the grain
# clears itself. Losing the tier mid-flow costs one more `cyc login`. Bounded by concurrent device
# sign-ins, and polled every five seconds while pending, which is a write rate the durable tier's
# synchronous replication should never see.
#
# InvitationGrain is one invitation of an address into a tenant (#43, docs/plan/11 § Sign-up and
# tenant creation, the invited path), and DURABLE for the question docs/plan/05 § Choosing a tier
# asks: its loss is a colleague holding a link they were told would work for seven days and that
# answers "not valid" — a dead end a person notices, with no way to rebuild the record from anything
# else (the link's secret is kept only as a digest, by design). Written a handful of times per
# invitation, so the durable tier's write cost is nothing; the invited user it created is in the
# durable tier already, and an invitation that outlived a hot-tier flush while its user did not would
# be the worse split.
CyberCloud.Identity.Grains.InvitationGrain
#
# DirectoryIndexGrain is the list of a tenant's users, invitations or applications (#41, the identity
# administration pages), and DURABLE because it is the only thing that can enumerate them: every one
# is keyed by a random id, the email and client indexes are keyed by digests, and so "rebuildable by
# scanning" means scanning the durable store — the incident-time operation the indexes above exist
# to avoid. Its loss is a member no administrator can see, list or remove. Written once per created
# object; read by an owner opening a page.
CyberCloud.Identity.Grains.DirectoryIndexGrain
