# module-layering.txt — which module may reference which.
#
# docs/plan/03 § Assembly graph rules, rule 7: "Every edge between two modules is declared here, and
# the declaration is acyclic." Enforced by the Assembly graph gate in build/Build.Architecture.cs.
#
# A MODULE is an assembly name truncated to its first two dotted segments, so CyberCloud.Identity
# and CyberCloud.Identity.Contracts are one module — the .Contracts seam is internal to a module and
# is not what this file is about. A provider's module is its family: CyberCloud.Providers.Sample and
# CyberCloud.Providers.Sample.Contracts are one. src/Hosts and cli/ are out of scope; a host is the
# composition root, referencing modules is its job, and nothing references a host, so no host can be
# part of a cycle. What a host may reference is rules 4 and 5.
#
# Enforced in three directions, each catching a different mistake:
#
#   * an edge in the shipping graph that is not a line here is a coupling nobody reviewed;
#   * a line here with no edge behind it is standing permission for a coupling nobody reviewed —
#     the next person to need it will find it already granted;
#   * a cycle in the lines below is two modules that have become one, and no line may declare that.
#
# ⚠ ADDING A LINE IS A REVIEW REQUEST, NOT A BUILD FIX. The question a reviewer is being asked is
# "may this module take a dependency on that one, forever" — module independence is what lets an
# OTP delivery fail without taking sign-in down (docs/plan/17, and the ⚠ blocks in
# CyberCloud.Communication.csproj that say which modules it will not reference and why). If the
# honest answer is "it should go through a seam instead", the line does not belong here.
#
# ⚠ WHAT THIS FILE CANNOT SEE. Rule 7 reads the AssemblyRef table and the ProjectReference set. Both
# miss a dependency expressed some other way — a resource id, a grain key, a string that names a
# type. That is the point: docs/plan/03 § Assembly graph rules, rule 2 sends cross-provider traffic
# "through CyberCloud.ResourceManager by resource id" precisely so that it is not an assembly edge,
# and the same holds between modules. An empty column here is not proof of independence at runtime.
#
# One "Module -> Module" per line. Blank lines and lines starting with `#` are ignored. Test
# projects are out of scope; the gate reads shipping assemblies only.

# ── The floor ──────────────────────────────────────────────────────────────────────────────────
# CyberCloud.Core references nothing at all — that is rule 1, and it is why it appears only on the
# right of an arrow. Everything below reaches it, most of them through CyberCloud.Core.Contracts.
CyberCloud.Authorization -> CyberCloud.Core
CyberCloud.Communication -> CyberCloud.Core
CyberCloud.Kubernetes -> CyberCloud.Core
CyberCloud.ServiceDefaults -> CyberCloud.Core
CyberCloud.Tenancy -> CyberCloud.Core

# ── Tenancy — docs/plan/06 ─────────────────────────────────────────────────────────────────────
# The tenant and the shard map. It takes telemetry and health wiring from ServiceDefaults; nothing
# comes back the other way, which is what keeps ServiceDefaults referenceable by a host that has no
# tenants at all.
CyberCloud.Tenancy -> CyberCloud.ServiceDefaults

# ── The platform services ──────────────────────────────────────────────────────────────────────
# Metering is billing: it reaches tenancy for the tenant a usage record belongs to, and nothing
# reaches metering. CyberCloud.Communication.csproj § "WHY THIS DOES NOT REFERENCE
# CyberCloud.Metering" is the other half of that sentence — the send path must not be able to be
# slowed or failed by billing, so the edge exists in one direction only.
CyberCloud.Metering -> CyberCloud.Core
CyberCloud.Metering -> CyberCloud.Tenancy

# ⚠ CyberCloud.Communication reaches CyberCloud.Core and NOTHING ELSE, and that is the single most
# load-bearing absence in this file. docs/plan/17 makes the platform the sending module's first
# customer — identity, monitor and billing all call INTO it. An edge the other way would let an OTP
# delivery take the identity module down with it, which is exactly backwards for the module that
# gates sign-in. The reverse edge below is the one that is allowed.
CyberCloud.Identity -> CyberCloud.Communication

# ── Identity — docs/plan/11 ────────────────────────────────────────────────────────────────────
# Identity is a consumer of everything under it and a supplier to nothing here: only hosts and the
# gateway reach it, and neither is in scope for this rule.
#
# ⚠ THE LINE BELOW IS NOW A BOUND EDGE, AND THE PARAGRAPH THAT USED TO BE HERE WAS WRONG ABOUT WHY
# IT WAS NOT. It read: "this line exists only in a .csproj … a rule 7 built on binding references
# would not merely have missed this edge, it would have called this line stale and asked for it to
# be deleted." The first half was true of one ASSEMBLY — CyberCloud.Identity referenced the
# CyberCloud.Authorization implementation for ObjectTypes and Relations, every member of both a
# `const string`, so that assembly's AssemblyRef table genuinely had no row. The conclusion did not
# follow, because rule 7 is a MODULE rule: CyberCloud.Identity.Contracts binds SubjectRef and
# ObjectRef from CyberCloud.Authorization.Contracts, ModuleOf() truncates both names to two
# segments, and so this exact line was already produced by a bound edge. A metadata-only rule 7
# would have kept it, not deleted it.
#
# The `const` blind spot is real; this was not a live instance of it. The vocabulary has since been
# lifted into CyberCloud.Authorization.Contracts (AuthorizationVocabulary.cs) and
# CyberCloud.Identity's ProjectReference on the implementation assembly is gone, so nothing in the
# tree now depends on the ProjectReference half of rule 7 to see an edge. That is an argument for
# keeping it — an unexercised half of a rule is the half that rots — not against.
#
# ⚠ CyberCloud.Identity.Validation IS IN THIS MODULE AND ADDS NO LINE. It is the relying-party half
# of docs/plan/11 § Protocol — the bearer-token validator the gateway and the feeds host share —
# and it references CyberCloud.Identity.Contracts and CyberCloud.Core only, both already covered.
# ModuleOf() folds it into CyberCloud.Identity; the boundary that matters about it is not a module
# edge but a HOST one: CyberCloud.Identity.Host must never reference it, and its .csproj says why.
CyberCloud.Identity -> CyberCloud.Authorization
CyberCloud.Identity -> CyberCloud.Core
CyberCloud.Identity -> CyberCloud.Tenancy

# ── The resource manager — docs/plan/08 ────────────────────────────────────────────────────────
# Authorization for the ReBAC check, Kubernetes for the fabric it projects onto, tenancy for the
# tenant a resource id resolves within.
#
# ⚠ NO EDGE TO CyberCloud.Identity, AND ISSUE #86 IS WHERE IT WAS ASKED FOR FIRST. A role assignment
# must refuse a principal the directory does not hold, and the directory is four identity grains —
# so the obvious line is this module reaching CyberCloud.Identity.Contracts for IUserGrain and its
# siblings. It is not here, for the reason the vault's paragraph above gives in the other direction:
# a line is standing permission, and the identity module's sign-up flow (docs/plan/11 § Sign-up and
# tenant creation: "create tenant → create default subscription and resource group") is the first
# thing that will want the REVERSE edge, which this line would turn into a cycle. The lookup goes
# through IPrincipalDirectory in CyberCloud.ResourceManager.Contracts — shaped like CallerContext, a
# type and an id — with a refusing default in this module and the real implementation,
# GrainPrincipalDirectory, in the gateway host: the one shipping assembly that references both
# contracts assemblies, and outside this rule's scope by rule 7's own terms.
CyberCloud.ResourceManager -> CyberCloud.Authorization
CyberCloud.ResourceManager -> CyberCloud.Core
CyberCloud.ResourceManager -> CyberCloud.Kubernetes
CyberCloud.ResourceManager -> CyberCloud.Tenancy

# ── The vault — docs/plan/18 ───────────────────────────────────────────────────────────────────
# CyberCloud.Vault is the platform's OpenBao client: the one ISecretResolver that returns a value.
# It reaches CyberCloud.ResourceManager for that interface (it lives in
# CyberCloud.ResourceManager.Contracts) and CyberCloud.Core for SecretRef and Result.
#
# ⚠ THE DIRECTION IS THE WHOLE REVIEW, AND THE REVERSE EDGE WOULD BE A CYCLE. The obvious wiring is
# for AddCyberCloudResourceManager to register the OpenBao resolver directly, and it cannot:
# CyberCloud.ResourceManager -> CyberCloud.Vault plus the line below is two modules that have become
# one, and the third direction of this file refuses it. So the resource manager keeps
# UnavailableSecretResolver as its TryAdd default and never learns this module's name, and a host
# that has a vault calls AddOpenBaoSecretResolver — which is also what keeps the refusing default
# the default for every silo that does not.
#
# ⚠ NO EDGE TO CyberCloud.Identity, AND IT IS THE ONE THAT WILL BE ASKED FOR FIRST. Identity's
# ITotpSecretSeam is four lines over ISecretResolver and UnavailableTotpSecrets' own remarks name
# the adapter as intended — "in a host that already references both". A line here would make the
# module that gates sign-in depend on the module that reads the vault, which is the same shape
# CyberCloud.Communication refuses one section above and for the same reason.
CyberCloud.Vault -> CyberCloud.Core
CyberCloud.Vault -> CyberCloud.ResourceManager

# ── Object storage — docs/plan/13 § Artifact feeds, docs/plan/15 § Object storage ──────────────
# CyberCloud.ObjectStorage is the platform's S3 client: the one IObjectStore that stores bytes. The
# same two edges as the vault, for the same reason — the seam lives in
# CyberCloud.ResourceManager.Contracts beside ISecretResolver, the refusing default lives in
# CyberCloud.ResourceManager, and the reverse edge would be the cycle the vault's paragraph
# describes. A host that has a bucket calls AddS3ObjectStore; every other host keeps
# UnavailableObjectStore, which refuses by name.
CyberCloud.ObjectStorage -> CyberCloud.Core
CyberCloud.ObjectStorage -> CyberCloud.ResourceManager

# ── The resource graph — docs/plan/08 § The resource-graph projection, docs/plan/04 § Streams ────
# CyberCloud.ResourceGraph (#54) is the resource-changed stream's publisher over NATS JetStream and
# the projector that consumes it into a per-tenant ClickHouse table. The first two edges are the
# vault's and the object store's, for the same reason: IResourceChangedSink lives in
# CyberCloud.ResourceManager.Contracts and the logging default in CyberCloud.ResourceManager, and
# the reverse edge would be a cycle. The Tenancy edge is ProvisioningState, which the row carries
# and which lives in CyberCloud.Tenancy.Contracts (the resource manager's own contracts say why).
#
# ⚠ THE AUTHORIZATION EDGE IS THE ONE TO READ TWICE. CyberCloud.ResourceManager.Contracts
# deliberately does NOT reference CyberCloud.Authorization.Contracts, so that a provider cannot
# name the engine (docs/plan/07 § The enforcement seam). This module is not a provider: it fills
# the projection's access column from ICheckGrain.ListRoleAssignmentsAsync — the role-assignment
# view over the parent chain — which is the object-to-subjects question the column asks, and the
# one ReBacRoleAssignmentStore already reads for the same reason. CyberCloud.Identity and
# CyberCloud.ResourceManager hold the same edge; this is the third module to, and it takes it for
# a read.
CyberCloud.ResourceGraph -> CyberCloud.Authorization
CyberCloud.ResourceGraph -> CyberCloud.Core
CyberCloud.ResourceGraph -> CyberCloud.ResourceManager
CyberCloud.ResourceGraph -> CyberCloud.Tenancy

# ── Providers — docs/plan/03 § The .Contracts split ────────────────────────────────────────────
# A provider declares a ProjectReference on CyberCloud.ResourceManager.Contracts and
# CyberCloud.Kubernetes.Contracts and nothing else; the CyberCloud.Core and CyberCloud.Tenancy edges
# below are types bound THROUGH those two — ResourceId, ResourceTypeName, TenantId — and are here
# because rule 7 declares what is reached, not what is written down in a .csproj.
#
# ⚠ NO LINE BETWEEN TWO PROVIDERS MAY EVER BE ADDED HERE. Rule 2 forbids it outright and rule 7
# cannot grant what rule 2 refuses: cross-provider traffic goes through CyberCloud.ResourceManager
# by resource id. A line here would fail rule 2 and be deleted, not honoured.
#
# ⚠ "THROUGH CyberCloud.ResourceManager BY RESOURCE ID" HAS A NAME NOW, AND IT IS NOT AN EDGE IN THIS
# FILE. Issue #90 asked how a backup vault reads the file share it protects, or a bucket resolves a
# customer-managed key, when neither may reference the other's assembly. The answer is
# IResourceView and IResourceWatch on ReconcileContext — docs/plan/08 § What the resource manager
# deliberately does not do — a read-only view checked by the gateway's own authorizer with the
# OWNING resource as the subject, and a per-subscription watch on a resource type. Both live in
# CyberCloud.ResourceManager.Contracts, which every family already reaches, so the seam adds no line
# below and never will: a provider that wants another provider's resource gets a ResourceId into its
# desired body and asks the view. What the seam did add is rule 8 in the Assembly graph gate, which
# fails a provider that names the manager's grain interfaces or write seams directly — the road this
# file cannot see (the paragraph above, "WHAT THIS FILE CANNOT SEE") is now watched from the type
# table. ⚠ And the CyberCloud.ResourceManager line each family carries below is WIDER than the family
# needs: it is there for the .Application's AddCyberCloudProvider call, and it would also let the
# implementation project take a ProjectReference on the manager and call ResourceViews.For(anybody).
# This file cannot say "the .Application project only" — a module is a family — so rule 8 says it:
# an implementation or .Contracts project that references CyberCloud.ResourceManager fails the gate,
# whatever this file allows.
#
# ⚠ THE TWELVE FAMILIES BELOW HAVE IDENTICAL COLUMNS, AND THAT IS THE MEASUREMENT RATHER THAN A
# COINCIDENCE. docs/plan/25 § R1 asks what a provider costs the platform; four edges, the same four
# every time, is the answer for a trivial provider, for one with backup and pooling and extensions,
# for one that does quantity arithmetic and talks to a third operator, for one with two resource
# types in it, and — since 2026-08-12 — for one whose row is not even in docs/plan/12.
# CyberCloud.Providers.Storage is the first family from another catalogue document and it needed the
# same four; CyberCloud.Providers.Analytics is the first that renders TWO custom resources in TWO API
# groups and wires one to the other, and it needed the same four. A family arriving with a FIFTH edge
# is the signal that something has been reached for that a provider should have gone through
# CyberCloud.ResourceManager to get.
#
# ⚠ AND CyberCloud.Providers.Storage IS THE FIRST FAMILY WITH A REASON TO WANT A FIFTH. An HA
# SeaweedFS filer needs a shared metadata store, and this platform runs a managed PostgreSQL one
# namespace away — see charts/managed/seaweedfs/conformance.yaml § owed,
# `filer-is-a-single-point-of-failure`. The line is NOT here, because rule 2 forbids it and the
# sanctioned route is a resource id through CyberCloud.ResourceManager. Recorded so that the first
# author who wants the edge finds the refusal and the alternative in the same place.
#
# ⚠ AND CyberCloud.Providers.Analytics IS THE SECOND FAMILY WITH A REASON TO WANT A FIFTH — the same
# reason, from the other end of the same edge. docs/plan/12's ClickHouse row asks for "S3-backed disks
# for cold storage tiers", whose endpoint and access-key pair belong to a CyberCloud.Storage/accounts
# resource; charts/managed/clickhouse/conformance.yaml § owed, `s3-cold-tier`. Two families now want
# the SAME line for two different features, which is what turns "a provider might reach for this" into
# evidence that the sanctioned route needs a reader a reconciler can actually call. The line stays out.
#
# ⚠ AND CyberCloud.Providers.ContainerService IS THE FAMILY THAT WAS EXPECTED TO NEED A FIFTH EDGE AND
# DOES NOT. It is the first whose PRODUCT is a Kubernetes cluster: the kubeconfig it causes to exist is
# what would let the platform reach that cluster, and CyberCloud.Kubernetes is where
# IClusterConnectionGrain.AttachAsync lives. A line to that IMPLEMENTATION assembly would be the
# obvious way to register the new cluster as a connection, and it is not here — a provider may
# reference CyberCloud.Kubernetes.Contracts only (docs/plan/03 § The .Contracts split), and attaching
# a connection is the resource manager's job rather than a reconciler's.
#
# ⚠ THE REFUSAL HELD AND THE CONSEQUENCE IS NOW PAID FOR, BY A SEAM ABOVE THE PROVIDER RATHER THAN BY
# A LINE HERE. This paragraph used to end "a cluster this provider creates is NOT reachable as a
# clusterId afterwards, and nothing in the whole tree calls AttachAsync outside a test", which was
# true for as long as there was nowhere else for the write to live. There is now:
# IClusterConnectionRegistrar in CyberCloud.ResourceManager.Contracts, implemented by
# GrainClusterConnectionRegistrar in CyberCloud.ResourceManager — an assembly that already reaches
# CyberCloud.Kubernetes.Contracts, and whose edge to this module is the one declared below. The
# reconciler REPORTS what it produced through ReconcileContext.ClusterConnections and ReconcileDriver
# performs the attach, after the pass, and only when it converged. So the provider supplies the facts
# only it knows and the manager makes the write only it may, and this family still has four edges.
#
# ⚠ THE REVERSE EDGE IS WHAT MADE THE HOME OBVIOUS. Beside ClusterConnectionHandle is where the
# registrar belongs by shape, and CyberCloud.Kubernetes -> CyberCloud.ResourceManager is a cycle
# against the line already below. Rule 7 refusing it is what put the implementation on the correct
# side of the seam rather than the convenient one.
# See charts/managed/kubernetes/conformance.yaml § owed, `the-cluster-this-creates-is-not-connectable`,
# whose remaining half is the credential: nothing yet reads Cluster API's `{cluster}-kubeconfig`
# Secret out of the MANAGEMENT cluster.
# ⚠ That is the M1 exit story's FOURTH step — "create a VPC and a Postgres server in it".
# ⚠ AND CyberCloud.Providers.Network IS THE FIRST FAMILY THAT OTHER FAMILIES WILL WANT A LINE **TO**,
# WHICH IS THE OTHER DIRECTION AND THE SAME REFUSAL. Every family above wants a fifth line to reach
# something it needs; this one is the thing docs/plan/13's VMs and containers, docs/plan/14's own load
# balancers and docs/plan/12's private endpoints will each want to reach, because a workload that joins
# a tenant's VPC has to name one. Rule 2 forbids that line as firmly as it forbids the others, and the
# sanctioned route is the same: a resource id through CyberCloud.ResourceManager. Recorded BEFORE the
# first consumer exists, so that the author of the first VM provider finds the refusal and the
# alternative already written down rather than discovering the edge is easy and taking it.
#
# ⚠ FOUR EDGES, THE SAME FOUR, FOR THE TENTH FAMILY — over a family with FIVE resource types, three of
# them children, rendering four Kube-OVN kinds across one API group. The fifth-edge signal has still
# not fired from any provider's own needs.
#
# ⚠ AND STILL FOUR AFTER CyberCloud.Network/publicIpAddresses, WHICH IS THE FIRST TYPE IN THIS FAMILY
# THAT IS NOT INSIDE A VIRTUAL NETWORK. It draws QuotaMeter.PublicIps, which is the first draw of that
# meter in the platform — and that needs nothing new here, because CyberCloud.Tenancy is already one
# of the four. What it did NOT need is the interesting half: an OvnEip names no VPC, so the type has
# no parent and reaches no sibling. ⚠ The consumer that WILL want a line to it is docs/plan/14's own
# `loadBalancers`, which has to attach an address to a backend — and that is the same refusal and the
# same sanctioned route as the paragraph above, one type further in. The attachment is a second
# Kube-OVN object naming PublicIpAddresses.ObjectNameOf's output, which is derivable from a resource
# id alone, so the edge is not needed for the join — only for resolving the id, which is
# CyberCloud.ResourceManager's.
#
# ⚠ AND CyberCloud.Providers.ContainerRegistry IS THE THIRD FAMILY WITH A REASON TO WANT A FIFTH, AND
# THE FIRST WHOSE PLAN DOCUMENT ASKS FOR THE EDGE IN AS MANY WORDS. docs/plan/13 § Container Registry:
# "Storage backend is the tenant's SeaweedFS bucket, so registry storage is billed like any other
# blob." That bucket is a CyberCloud.Storage/accounts resource, its endpoint and access-key pair live
# behind another provider's vault path, and ReconcileContext still carries no resolver for another
# provider's resource. So the registry keeps its images on a PersistentVolumeClaim instead, which is
# the shipped shape and is a smaller product than the one docs/plan/13 describes —
# charts/managed/harbor/conformance.yaml § owed, `storage-backend-is-not-the-tenants-bucket`. The
# line stays out.
#
# ⚠ THREE FAMILIES NOW WANT THE SAME MISSING LINE, FOR THREE DIFFERENT FEATURES, AND TWO OF THE THREE
# WANT IT TO REACH CyberCloud.Storage/accounts SPECIFICALLY. Storage itself wants a Postgres for its
# filer; Analytics wants an S3 cold tier; this one wants an S3 registry backend. That is no longer
# "a provider might reach for this" — the sanctioned route (a resource id through
# CyberCloud.ResourceManager) has no reader a reconciler can call, and three rows have now shipped
# reduced because of it.
#
# ⚠ AND THE SAME FOUR FOR CyberCloud.Providers.Terminal, WHICH IS THE ONE THAT SHOULD HAVE BROKEN IT.
# A cloud terminal's whole purpose is to reach the tenant's OTHER resources — docs/plan/24's M1 exit
# story says "psql into it" in as many words — so this is the first family whose PRODUCT is
# cross-provider reach, and the obvious fifth line is to whatever knows where a tenant's databases
# live. It is not here, and the reason it was not needed is worth recording because it is not the
# usual "it would have been a shortcut": what the terminal renders is a NetworkPolicy over LABEL
# SELECTORS, and a label is a string. Reach expressed as a selector needs no reference to the thing
# selected. That is the first instance in this tree of rule 2 being satisfied by a MECHANISM rather
# than by a resource id, and it is cheaper than the sanctioned route rather than more expensive.
# ⚠ What it costs is that the selector is unverifiable from here: the tenant-wide rule matches
# namespaces nothing in this repository labels. See
# charts/managed/cloud-shell/conformance.yaml § owed, `namespaces-are-not-labelled`.
# ⚠ AND CyberCloud.Providers.Monitor WAS THE FAMILY MOST OBVIOUSLY OWED A FIFTH LINE AND TOOK NONE —
# for the two lines the naive reading wants. It takes a DIFFERENT fifth line since #32, declared with
# the Communication family below, and the two refusals here still stand word for word, because the
# line it takes is neither of them. The absence was worth more than the ten agreements above it, and
# it is worth the same now. docs/plan/16 makes the platform its own first customer — platform
# telemetry runs "under a platform workspace. No separate stack." — so the naive reading is that
# every module reaches CyberCloud.Providers.Monitor to emit, and that this family reaches
# CyberCloud.Metering to bill. NEITHER LINE EXISTS AND NEITHER MAY:
#
#   * NOTHING REACHES THIS FAMILY TO EMIT TELEMETRY. Emission goes to CyberCloud.Ingest.Host over
#     OTLP, which docs/plan/03 § Hosts makes deliberately NOT an Orleans client. If a module
#     referenced this one to publish a metric, telemetry would run through the control plane, and the
#     control plane's own reconcile would depend on a resource type whose reconcile emits telemetry.
#     That is the dependency cycle MonitorWorkspaces' clause 4 exists to refuse, and the empty column
#     here is what keeps it refused at compile time rather than by memory.
#   * THIS FAMILY REACHES NOTHING TO BILL. Retention and quota reach billing the way every other
#     provider's amounts do — through a declared MeterDerivation the resource manager reads — which is
#     an edge to CyberCloud.ResourceManager that line 4 below already grants.
#
# ⚠ WHAT IT DOES SHARE WITH CyberCloud.Providers.Network IS BEING A FAMILY OTHERS WILL WANT A LINE
# **TO**. docs/plan/16 § What the platform monitors about itself lists ten platform signals — grain
# call latency, reconcile queue depth, ReBAC check p99 — every one of which is produced by a module in
# this file. The route for all ten is the same and is not an assembly edge: OpenTelemetry through
# CyberCloud.ServiceDefaults, which every module already reaches, into a host that is not in this
# file's scope. Recorded BEFORE the first platform dashboard exists, so that whoever wires the tenth
# signal finds the refusal and the alternative rather than discovering the edge is easy.
#
# ⚠ FOUR EDGES, THE SAME FOUR, FOR THE TWELFTH FAMILY AS IT LANDED — over the first resource type in the catalogue
# whose product is not a workload at all. The fifth arrived with its second type (#32); see below.
CyberCloud.Providers.Analytics -> CyberCloud.Core
CyberCloud.Providers.Analytics -> CyberCloud.Kubernetes
CyberCloud.Providers.Analytics -> CyberCloud.ResourceManager
CyberCloud.Providers.Analytics -> CyberCloud.Tenancy
CyberCloud.Providers.Cache -> CyberCloud.Core

# ⚠ THE SECOND LINE BEYOND THE FOUR IN THIS FILE, AND THE FIRST FAMILY WITH ALL FIVE. #32:
# CyberCloud.Monitor/workspaces/alertRules names an action group — a CyberCloud.Communication/services
# resource, a ChannelKind and recipients — and its evaluator delivers through IMessageSender.
# docs/plan/16 § The stack's Alerting row says it in four words: "delivery is [17]". The line is to the
# .Contracts assembly for ChannelKind, IMessageSender, SendRequest and CommunicationGrainKeys, and the
# last of those is the join: the sending service's grain id is derived from its resource id PATH, so
# the rule reaches the tenant's service with no index read and no line to CyberCloud.Providers.Communication
# — which rule 2 forbids and this file would delete. docs/plan/03 § Assembly graph rules, rule 2's
# "through CyberCloud.ResourceManager by resource id", taken literally for the first time.
#
